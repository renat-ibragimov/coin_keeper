# 09. Миграция данных

Перенос из SQLite-базы десктопной версии в PostgreSQL. Разовая операция, но скрипт должен быть
воспроизводимым и идемпотентным — запускаться будет не один раз, пока не сойдётся.

## Персональные данные — правило без исключений

**Реальные email-адреса, пароли и любые другие персональные данные не попадают в репозиторий
никогда** — ни в документацию, ни в код, ни в тесты, ни в примеры команд, ни в сообщения
коммитов. Репозиторий публичный.

В примерах — только плейсхолдеры: `<owner-email>`, `<admin-email>`, `<домен>`. Настоящие
значения живут в `.env` на сервере, в GitHub Secrets и в голове администратора.

Это касается и вставки «просто чтобы показать, как выглядит»: адрес, единожды попавший
в git, остаётся в истории и после удаления файла.

## Владелец данных

Вся коллекция принадлежит одному человеку. Перед миграцией создаётся пользователь, и все
личные записи привязываются к его `id`.

**Аккаунт владельца рождается заполненным** — он не проходит регистрацию:

```
email_verified = true      письмо слать некуда и незачем: адрес известен заранее
is_active      = true      аккаунт работает сразу
role           = 'admin'   владелец ведёт общий каталог
```

Email и пароль задаются параметрами скрипта, в код не зашиваются и в репозиторий не
попадают (см. выше).

### Пароль владельца

Основной путь — `--owner-password`. Скрипт **спрашивает пароль интерактивно**, если значение
не передано: так он не оседает в истории оболочки и не виден в `ps` соседним процессам.
Передавать значение прямо в командной строке можно, но это осознанный компромисс для
автоматизации, а не рекомендуемый способ.

**Пароль проходит ту же валидацию, что и при обычной регистрации** — минимум 10 символов
и остальные правила из `07-auth.md`. Слабый пароль скрипт отклоняет и ничего не мигрирует.
Исключений «это же сидинг, тут можно попроще» нет: аккаунт владельца — админский, и он
сразу оказывается в интернете на публичном домене.

Хеширование — тот же argon2id, что и в приложении. Отдельной ветки кода для сидинга быть
не должно, иначе она разойдётся с основной.

Альтернатива — флаг `--send-reset`: вместо пароля владельцу уходит ссылка сброса, и он
задаёт пароль сам через обычную форму. Удобно, когда миграцию запускает не сам владелец.
Требует рабочего `MAIL_BACKEND=smtp` (`10-infra.md`).

### Второй администратор

Заводится **не скриптом, а штатной регистрацией через форму** — это осознанная проверка
пути нового пользователя на настоящем окружении: форма, письмо, верификация, вход. Если
где-то в этой цепочке дыра, лучше найти её на своём человеке, чем на постороннем.

После регистрации роль поднимается скриптом:

```
backend/scripts/promote_admin.py --email <admin-email>
```

Скрипт находит пользователя по email, ставит `role = 'admin'` и печатает подтверждение.
Требования:

- пользователь должен существовать и быть подтверждённым — `email_verified = false`
  означает, что регистрация не была доведена до конца, и роль поднимать рано;
- идемпотентность: повторный запуск на уже админе ничего не ломает и сообщает об этом;
- `--demote` для обратной операции;
- каждый запуск пишется в `audit_log`.

Интерфейса управления ролями в MVP нет — только этот скрипт (`07-auth.md`).

**Каталог из мигрированной базы становится общим.** Все 3063 позиции переносятся с
`created_by = NULL`: это затравка общего каталога, дальше его ведут администратор и системная
задача по каталогу НБУ (`04-business-rules.md`, п. 2). Личных позиций миграция не создаёт.

**Снимки цен переносятся как общие** (`created_by = NULL`): они пришли из внешних источников,
а не от пользователя, и после миграции их всё равно пересобирает центральная суточная
задача.

Идентификаторы сохраняем как есть (`INSERT` с явным `id`), после — сбрасываем последовательности:

```sql
SELECT setval('catalog_items_id_seq', (SELECT MAX(id) FROM catalog_items));
```

Так сохраняются все внешние ключи и не нужна таблица соответствия старых и новых id.

## Преобразования типов

| Поле | Было | Стало | Как |
|---|---|---|---|
| Все денежные | `REAL` | `numeric(14,2)` | округление до 2 знаков, проверять расхождение сумм |
| `rate_uah`, `purchase_rate_uah` | `REAL` | `numeric(14,6)` | 6 знаков — курсы НБУ бывают дробными |
| Даты (`acquisition_date`, `expense_date`, `effective_date`, `issue_date`) | `TEXT` | `date` | ISO уже, парсить строго; пустые → NULL |
| Моменты (`created_at`, `observed_at`, `fetched_at`) | `TEXT` | `timestamptz` | часть в ISO с `Z`, часть в формате SQLite `YYYY-MM-DD HH:MM:SS` без зоны — вторые считать UTC |
| Флаги (`is_for_swap`, `is_active`, …) | `INTEGER` 0/1 | `boolean` | |
| `collection_group`, `metal_kind`, `role`, `category`, `match_status` | `TEXT` + CHECK | ENUM | значения совпадают, привести к нижнему регистру |
| `raw_payload_json` | `TEXT` | `jsonb` | невалидный JSON → NULL, записать в отчёт |

до копейки — 42 765,66 грн. Не совпало — миграция неверна.

## Разделение путей изображений

Поле `original_path` содержало вперемешку два типа значений. Правило:

```
начинается с http://  или https://  → external_url = значение, storage_key = NULL
иначе                                → storage_key  = ключ загруженного в S3 файла
```

Ожидаемое распределение: 2796 внешних, 2270 локальных.

### Формат локальных путей

Здесь док раньше утверждал, что в `original_path` лежат голые имена файлов. **Это
неверно** — вскрылось на первом боевом dry-run. Десктопная версия работала под Windows и
записывала **полный абсолютный путь**: буква диска, обратные слеши, пробелы в именах
каталогов.

```
C:\Users\<пользователь>\AppData\Roaming\CoinKeeper Data\media\5_obverse_<uuid>.jpg
```

`pathlib.Path` на POSIX **не считает обратный слеш разделителем**, поэтому `.name` от
такого значения возвращает строку целиком, и файл ищется по имени
`C:\Users\...\5_obverse_<uuid>.jpg`. Результат первого прогона: 2270 локальных записей,
найдено 0 файлов.

**Правило извлечения имени:** берётся хвост после последнего разделителя, любого из `/`
и `\`; если после этого остался префикс вида `C:` (путь относительно диска), он
отбрасывается. Имя возвращается как записано, включая регистр расширения — файл ищется
на диске именно по нему.

Разделение external/local при этом не меняется: решает только схема `http://` и
`https://`, всё остальное — локальный файл.

### Происхождение изображений

Каждой переносимой записи проставляется `media_files.source` (`06-media-storage.md`):

```
external_url на i.ucoin.net (и любой домен ucoin)  → source = 'ucoin'
локальный файл, скачанный когда-то с uCoin          → source = 'ucoin'
локальный файл — собственная фотография владельца   → source = 'user_upload'
```

Различить два вида локальных файлов помогает `price_source_links` и `catalog_items.source_key`:
если у позиции есть ссылка на uCoin, её каталожные изображения почти наверняка оттуда.
Спорные случаи размечаются как `ucoin` — более строгий вариант; ошибка в эту сторону скроет
фото от посторонних, ошибка в обратную опубликует чужое.

Записи с `source = 'ucoin'` видны только владельцу исходной базы: он и есть тот пользователь,
который их импортировал. Для остальных в публичной карточке — плейсхолдер, пока задача по
каталогу НБУ не заменит украинскую часть официальными фото (`source = 'nbu'`).

Для локальных: файл ищется в `legacy/data/media/` по имени из `original_path`.
Уцелело 839 из 1681 — записи, для которых файла нет, помечаются и попадают в отчёт.
Строку в `media_files` при этом **не удаляем**, если у неё есть `external_url`;
если нет ни файла, ни ссылки — запись пропускается.

Загрузка в S3 идёт с обработкой по правилам `06-media-storage.md`: WebP, превью,
`sha256`, размеры.

## Валидация цен при переносе

3938 снимков содержат неизвестную долю мусора: парсер uCoin в legacy ошибался, ошибки
чинились точечными миграциями постфактум. Признак: оценка коллекции 313 400 грн при
затратах 42 766 грн — рост в 7,3 раза, что для этого набора монет неправдоподобно.

**Переносим все снимки** (история ценна сама по себе), но каждый прогоняем через проверки
из `05-integrations.md`, раздел «Валидация цены», и не прошедшие помечаем:

```
market_price_snapshots.is_suspect  boolean NOT NULL DEFAULT false
```

Колонка добавлена миграцией Alembic `0002` и описана в `02-data-model.md`.

**Правила применяются к унаследованным данным с двумя оговорками**, потому что часть из них
рассчитана на живой парсинг, а не на готовые строки:

- «Не год»: половина правила про «число в 1900–2100 при отсутствии символа валюты» может
  сработать только если `currency_code` пуст или неизвестен — в legacy он есть всегда.
  Работающая половина — цена, равная году выпуска своей же монеты.
- «Валюта явно определена»: исходного текста нет, поэтому проверяется записанный
  `currency_code` против фактического списка валют.

Снимок может нарушить несколько правил сразу — в отчёт попадают все, поэтому суммы по
правилам больше общего числа помеченных.

Подозрительные исключаются из расчёта текущей оценки коллекции, но остаются в истории
и видны в карточке монеты.

Скрипт выводит отчёт: сколько снимков помечено, по какому правилу, с примерами.
После миграции цены пересобираются заново — уже с валидацией на входе.

## Валюта покупок

В legacy `addPurchase` жёстко записывал `UAH` и курс `1`, игнорируя ввод. Поэтому все 620

## Форма скрипта

```
backend/scripts/migrate_legacy.py
  --sqlite   <path>      legacy-база SQLite
  --media    <path>      каталог с фотографиями
  --owner-email <owner-email>
  --owner-password       пароль владельца; без значения — интерактивный запрос
  --dry-run              только отчёт, без записи
  --skip-media           отложить шаг медиа целиком, для быстрой проверки
  --resume               продолжить на непустой базе
  --expect <file>        профиль ожидаемых чисел, проверяется в конце
  --report <file>        куда писать JSON-отчёт
```

`--owner-password` не должен попасть в историю команд с настоящим значением — см.
«Персональные данные». Без значения скрипт спрашивает пароль интерактивно, это
рекомендуемый путь.

**`--send-reset` в этапе 2 не реализован.** Он требует рабочего SMTP на сервере и
осмысленен только когда миграцию запускает не сам владелец; на практике её запускает
владелец и сразу задаёт пароль. Останется как возможное дополнение, если понадобится.

### Флаги, добавленные при реализации

- **`--resume`.** Прогон на непустой базе по умолчанию **останавливается** с ошибкой:
  молчаливое дописывание поверх существующих данных — худший из возможных исходов, потому
  что расхождение обнаружится нескоро. С флагом прогон продолжается, вставка идемпотентна
  по первичному ключу.
- **`--expect`.** Числа из чек-листа ниже вынесены в
  `backend/scripts/expected_legacy_2026-08-06.json`. Без флага скрипт всё равно сверяет
  результат с источником (это работает на любой базе); с флагом дополнительно требует,
  чтобы сам источник совпал с задокументированным профилем.
- **`--report`.** Путь к отчёту; по умолчанию рядом со скриптом.

Коды возврата: `0` — успех, `2` — аргументы или слабый пароль, `3` — не читается исходная
база, `4` — контрольные проверки не сошлись, `5` — миграция остановлена. **Ненулевой код
означает, что данным нельзя доверять.**

Требования:

- Идемпотентность: повторный запуск на непустой базе не создаёт дублей
  (проверка по `source_key` и `id`).
- Транзакционность по этапам: сбой на изображениях не откатывает каталог.
- Итоговый отчёт в JSON: перенесено по таблицам, пропущено, помечено, ошибки.
- В отчёт и в логи **не пишутся** пароли и email владельца — только `id` пользователя.

### Висячие ссылки в исходной базе

SQLite **не проверяет внешние ключи**, если явно не включить `PRAGMA foreign_keys` —
десктопная версия этого не делала. Значит, в исходной базе может лежать строка, ссылающаяся
на несуществующую запись: снимок цены с валютой, которой нет в `currencies`, расход на
удалённый экземпляр и так далее. PostgreSQL такие строки не примет.

Скрипт **проверяет ссылки до вставки**: строка с висячей ссылкой не переносится, попадает
в отчёт с указанием поля и значения, и учитывается в сверке. Без этого прогон падал бы
посреди работы с невнятной ошибкой драйвера, уже записав несколько таблиц.

### Что означает `--skip-media`

Флаг **откладывает шаг медиа целиком**, а не переносит записи без файлов. Иначе в базе
появились бы строки с `storage_key`, указывающим на объект, который никогда не загружался,
и строки для файлов, которых нет — их отсутствие без обработки просто не заметить.

Порядок «сначала быстро, потом с картинками» работает: повторный прогон без флага
дозаполняет `media_files`, вставка идемпотентна.

### Владелец у мигрированных изображений

Всем переносимым записям `media_files` проставляется `owner_id` владельца — включая
каталожные. В `02-data-model.md` сказано «NULL для каталожных», и для изображений, которые
появятся позже, это верно. Но правило видимости `source = 'ucoin'` — «виден только тому,
кто импортировал; для мигрированных — владельцу исходной базы» — требует, чтобы этого
человека можно было опознать. Без `owner_id` опознать его нечем.

## После миграции

1. Проверить выборочно 10–15 монет: характеристики, фото, цена, покупка.
2. Запустить фоновую загрузку изображений по `external_url`. Скачанные файлы **наследуют
   `source` записи**: пришло с uCoin — остаётся `'ucoin'` со своим правилом видимости.
