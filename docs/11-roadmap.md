# 11. Порядок работ

Этапы упорядочены так, чтобы каждый заканчивался **проверяемым результатом**, а не
«написали слой». Следующий этап не начинается, пока не выполнен критерий приёмки предыдущего.

**Текущее состояние (2026-09-03): этапы 0–3 завершены, API задеплоен на
`coins.renat-ibragimov.com`. Этап 4 в работе: готовы часть 1 (каркас, дизайн-система,
вход, каталог) и часть 2 (дашборд «Огляд», карточка монеты с историей цен). Следующая —
часть 3: коллекция и добавление покупки, личные позиции, серии, «Не вистачає»,
настройки, выкладка фронтенда из CI. После части 3 — веха «Демо».**

Правило ведения: каждая завершённая часть этапа обновляет этот документ и затронутые
доки тем же набором коммитов (`CLAUDE.md`, «Правила работы с кодом»).

Чек-лист первого деплоя из `10-infra.md` пройден целиком.

Этап заканчивается работающим контуром: код из `main` живёт на домене, а не на ноутбуке.
Дальше каждый следующий этап выкатывается тем же способом, и «у меня локально работает»
перестаёт быть валютой.

Обязательный тест на каскады: **удаление пользователя, имеющего личные позиции каталога и
экземпляры на них, проходит одним стейтментом и не оставляет осиротевших строк.** Это проверка
каскадного ромба `users → collection_items` и `users → catalog_items` — заодно с тем, что
общий каталог при удалении пользователя не страдает. Второй тест рядом проверяет, что
внешний ключ по-прежнему не даёт оставить экземпляр без позиции каталога
(`02-data-model.md`, «Почему `NO ACTION`, а не `RESTRICT`»).

## ◆ Контрольная точка: демо владельцу коллекции

Не этап, а веха между этапами 4 и 5 — назначается по завершении части 3 этапа 4. Ничего не разрабатывается — приложение показывается
живым людям, и по итогам пересматриваются приоритеты этапов 5–6.

К этому моменту работает всё, что нужно для настоящей работы с коллекцией: каталог,
коллекция, покупки, деньги, серии, личные позиции. Не работает автоматика цен и импорт —
именно про них и нужно понять, что важнее.

**Что показываем:**

- **Владелец коллекции** входит под своим аккаунтом и видит **свою** коллекцию: 620
  экземпляров, реальные суммы, свои фотографии. Не демо-данные — его настоящая база,
  перенесённая в этапе 2.
- **Второй администратор** проходит путь нового пользователя целиком и на глазах:
  регистрация → письмо → верификация → вход → пустой дашборд. Пустое состояние — часть
  демонстрации, а не то, что прячут: именно его увидит каждый новый человек.

**Что собираем:** замечания и идеи, без немедленной реализации. Всё записывается, потом
раскладывается по этапам 5–6 и разделу «После MVP». Демо — источник приоритетов, а не
очередь задач на завтра.

**Правило до демо:** в этапах 1–4 ничего из этапов 5–6 не реализуется наперёд. Соблазн
«раз уж я здесь, добавлю кнопку обновления цены» надо гасить: смысл вехи в том, чтобы
приоритеты определялись увиденным, а не тем, что успели написать заранее. Заготовки под
будущее в схеме — можно и нужно (это уже заложено); работающая функциональность — нет.

## Этап 7. Продакшн-закалка

Сервер, домен, HTTPS и автоматическая выкладка работают с этапа 1 — здесь не разворачивание,
а доведение до состояния, в котором систему не страшно оставить без присмотра.

- **Бэкапы**: база по расписанию, синхронизация MinIO на внешнее хранилище, ротация
- **Проверка восстановления**: бэкап развёрнут в отдельную базу и сверён по количеству
  записей. Бэкап, который ни разу не разворачивали, — не бэкап
- **PWA**: манифест, иконки, установка на домашний экран
- Расписание системных задач включено, задачи отработали хотя бы раз на боевых данных
- **Финальный чек-лист безопасности**: firewall, SSH по ключу, закрытые наружу порты
  Postgres/Redis/MinIO, CORS только на домен фронтенда, отсутствие секретов в логах,
  автоматические обновления безопасности (`10-infra.md`)

**Критерий приёмки:** чек-лист продакшн-закалки из `10-infra.md` пройден целиком; бэкап
восстановлен и сверён; владелец пользуется приложением с телефона как основным
инструментом; **посторонний человек регистрируется сам**, получает письмо, подтверждает
адрес и заводит свою коллекцию.

## После MVP

Приоритет определяется по мере использования:

| Задача | Условие |
|---|---|
| «Повышение» личной позиции в общий каталог админом | когда станет видно, что за позиции заводят пользователи и какие из них стоит сделать общими |
| Слияние дубликатов общего каталога с перепривязкой экземпляров на каноническую позицию | до тех пор дубликаты закрываются архивацией с причиной `'дубликат'`; кандидатов даёт отчёт задачи НБУ |
| Продажи (`sales`) | если появится потребность |
| Цели коллекционирования | если появится потребность |
| Предложения о покупке | если появится потребность |
| Разновидности | сначала решить, нужны ли вообще |
| Numista | только с пользовательским API-ключом; закрыл бы цены США и СССР |
| OAuth (Google), 2FA | по желанию |
| Мобильные приложения (React Native / Expo) | после стабилизации API |

## Как вести работу

Одна задача — один этап или его часть. Перед началом читать документ, который её описывает:
ссылки указаны в каждом этапе. Отклонения от документации допустимы, но документ тогда
обновляется в том же изменении — расхождение между `docs/` и кодом хуже, чем отсутствие
документа.
